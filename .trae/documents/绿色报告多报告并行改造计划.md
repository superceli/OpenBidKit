# 绿色报告多报告并行改造计划

## Context

当前绿色报告一次只能生成一份：`green_report_meta` 固定 `id = 1`，目录节点没有 `report_id`，任务服务按任务类型全局互斥。用户提交生成后必须等待完成，才能开始下一份报告。

目标：改为“报告列表 + 多报告并行后台生成”。提交生成（首次点“生成目录”或“生成正文”）时把报告加入列表；用户可以立刻新建下一份报告并提交；列表展示每份报告的企业名、当前步骤、进度、状态，支持打开、取消、导出、删除。同一份报告内目录与正文仍互斥，不同报告可并行，最多同时生成 2 份，超出排队。

## 方案总览

- 引入 `report_id`（uuid）作为报告实例标识，迁移现有单例数据为一份历史报告。
- 绿色报告一级菜单下增加列表视图，`GreenReportHome` 内部用 `view: 'list' | 'wizard'` 切换，不新增一级导航。
- 任务实例 key 改为 `${type}:${reportId}`，事件携带 `reportId`，Renderer 按报告路由进度。
- 全局最多 2 份报告同时生成，超出的任务标记 `queued` 排队，前一份结束后自动启动。

## 阶段 1：数据库 v31

文件：`client/electron/services/sqliteDatabase.cjs`、`sql/workspace_schema.sql`

1. `schemaVersion = 31`，`migrations` 追加 `migrateGreenReportMultiReport`。
2. 新表结构（先建 `_v31` 表，搬数据后 rename）：
   - `green_report_meta`：`id TEXT PRIMARY KEY`，保留现有字段，新增 `report_seq`、`status TEXT NOT NULL DEFAULT 'draft'`、`progress INTEGER NOT NULL DEFAULT 0`。
   - `green_report_outline_nodes`：`report_id TEXT NOT NULL, node_id TEXT NOT NULL, ...`，`PRIMARY KEY(report_id, node_id)`，索引 `(report_id, parent_node_id, sort_order)`。
   - `green_report_tasks`：`report_id TEXT NOT NULL, type TEXT NOT NULL, ...`，`PRIMARY KEY(report_id, type)`。
3. 迁移逻辑：
   - 读旧 `green_report_meta WHERE id = 1`；若存在有效 `project_info_json`，生成 `report_id = uuid()`。
   - 复制旧 meta、outline nodes（全部写入该 report_id）、tasks（两行）。
   - 旧 `running/pausing/queued` 任务统一改为 `error`，错误信息“上次任务因应用关闭而中断”，meta 同步为 `error`。
   - `DROP` 旧三表，`RENAME` 新表，重建索引。
   - 无旧数据时只建新表，不创建空报告。
4. 同步 `schemaHealthTableGroups`：三张表条目版本提到 31；`repair` 指向新的 `createGreenReportSchema`。
5. 更新 `sql/workspace_schema.sql`：`user_version = 31` 与三张表定义。

## 阶段 2：Store

文件：`client/electron/services/greenReportStore.cjs`

1. 所有方法首参改为 `reportId`：`loadMeta`、`loadOutlineTree`、`loadTasks`、`loadState`、`saveMeta`、`updateStep`、`saveReportType`、`saveProjectInfo`、`saveOutlineConfig`、`saveReportConfig`、`saveKnowledgeContext`、`saveOutline`、`saveChapterContent`、`clearAllChapterContent`、`saveOutlineFromResult`、`saveTaskState`、`updateGreenReportWithoutReload`。
2. 新增：
   - `listReports()`：`SELECT id, report_type, project_info_json, step, status, progress, updated_at FROM green_report_meta ORDER BY updated_at DESC`，JS 解析企业名，返回 `{ id, companyName, reportType, step, status, progress, updatedAt }`。
   - `createReport({ reportType })`：uuid、默认 projectInfo、生成报告编号，返回 `loadState(reportId)`。
   - `deleteReport(reportId)`：事务内删 meta / nodes / tasks；IPC 层先校验无活动任务。
3. `saveTaskState` 改为 `INSERT ... ON CONFLICT(report_id, type) DO UPDATE`；写入后聚合 meta 状态：任一 `running` → `running`；`queued` → `queued`；否则按 `error > cancelled > success > draft` 取值。
4. `loadState(reportId)` 返回结构与现在一致，避免前端大改。

## 阶段 3：任务服务

文件：`client/electron/services/taskService.cjs`

1. 任务定义：绿色报告两个任务改 `lockPolicy: 'scope-exclusive'`，`getScopeId(payload) => payload.reportId`。
2. Map key 统一 `taskKey(type, reportId)`；任务对象增加 `report_id` 字段。
3. 互斥规则：
   - 同一 `reportId` 已有任一活动任务 → 抛“该报告正在生成，请等待完成或取消”。
   - 不同 `reportId` 不互斥。
4. 并发排队：
   - `MAX_CONCURRENT_REPORTS = 2`。
   - `startManagedTask` 拆为 `enqueueManagedTask`（校验、入 `pendingQueue` 或直接启动）与 `launchTask`（现有执行体）。
   - 排队任务状态 `queued`，写入 store 并 emit；任务结束后 `pumpQueue()` FIFO 启动下一个。
5. 事件：`buildSnapshot` 绿色报告返回 `{ reportId, greenReportPatch: loadState(reportId) }`；报告已被删除时返回 `{ reportId }`。
6. 取消：
   - `cancelTask(type, reportId)`；`queued` 从队列移除并标记 cancelled；`running` 走 AbortController。
   - 新增 `cancelReportTasks(reportId)`、`hasActiveTask(reportId)`。
7. 中断恢复：遍历 tasks 表中 `running/pausing/queued` 行，按报告置 `error`，并修正 meta 状态；合并现有重复定义的 `recoverInterruptedGreenReportTasks`。
8. `greenReportTasks.cjs` 通过 `withReportScope(store, reportId)` 适配，内部 store 调用保持原签名。

## 阶段 4：IPC / preload / types

文件：`electron/ipc/greenReportIpc.cjs`、`electron/ipc/index.cjs`、`electron/preload.cjs`、`src/shared/types/ipc.ts`

- 新增 `green-report:list`、`green-report:create`、`green-report:delete`。
- `load-state`、`update-step`、`save-*` 增加 `reportId`；`tasks:start-green-report-outline/content` 要求 `payload.reportId`。
- 取消接口改为按 `(reportId, type)`，新增 `tasks:cancel-green-report(reportId)`。
- 类型新增 `GreenReportSummary`；`TaskEventTask` 增加 `report_id`；所有 start/cancel 签名更新。
- 更新调用点：`GreenReportHome.tsx`、`CompanyInfoPage.tsx`、`OutlinePage.tsx`、`ContentPage.tsx`、`ExportFormatPage.tsx`（导出测试改为取最新一份有正文的报告）。

## 阶段 5：前端

文件：`src/features/green-report/pages/GreenReportHome.tsx`、新增 `GreenReportList.tsx` 与 `greenReportExportPayload.ts`、`feature-green-report.css`

1. `GreenReportHome` 默认 `view = 'list'`：
   - 列表卡片：企业名、报告类型、步骤标签、状态徽标、进度条、更新时间。
   - 操作：打开（进入向导）、取消（queued/running）、导出、删除（有活动任务时禁用）。
   - “新建报告”调用 `createReport()` 后进入向导。
2. 向导绑定 `reportId`，所有读写带该 id；步骤切换只更新当前报告。
3. 提交生成后：toast 提示“已提交，可返回列表新建下一份”，不阻塞；用户可继续停留在向导或返回列表。
4. `onTaskEvent` 只处理 `event.reportId === 当前报告 id`；列表同步更新该报告状态，终态时刷新 `listReports()`。
5. `buildExportPayload` 抽成纯函数，列表导出时先 `loadState(reportId)` 再组装。
6. 保留离开守卫：生成中离开页面不取消任务，返回列表可见进度。

## 风险与回滚

- 迁移失败：现有 `applyMigrations` 每个 migration 单事务并自动备份，失败恢复 `.backup-*` 文件即可；上线前先做迁移单测。
- 运行中删除报告：拒绝删除，提示先取消，避免 checkpoint 写入已删行。
- 并发写放大：`saveOutlineTree` 目前全量重写，并行时建议改为按 nodeId 增量更新或 300-500ms 节流。
- 事件风暴：每次事件带全量 `outlineData`，Renderer 必须按 reportId 过滤，避免两份报告互相覆盖。
- 旧版客户端打开 v31 库会拒绝启动；降级需同时恢复备份文件。

## 验证

1. 迁移单测（`node --test`）：临时库构造 v30 单例数据 → 跑迁移 → 断言 meta 1 行、nodes 全部带 report_id、tasks 2 行且状态 error、`user_version = 31`；空库迁移不产生报告。
2. 并行：创建 A/B 两份报告，分别提交目录生成，确认事件 `reportId` 正确、界面互不覆盖；第三份进入 queued，前一份完成后自动开始。
3. 同报告互斥：A 目录生成中提交正文应被拒绝；B 不受影响。
4. 取消：queued 取消后不再启动；running 取消后状态 cancelled 且无后续事件。
5. 导出隔离：A/B 分别导出，核对企业名、报告编号、封面字段、模板、知识库上下文与图片互不串。
6. 重启恢复：生成中强杀应用 → 重启后列表显示该报告 `error`，可重新生成。
7. 构建校验：`cd client; node --check electron/services/*.cjs; npm run build`。
